# 支付账本与对账核心（本地可运行）

一套仅依赖 Go 标准库、可完全离线运行的支付账本核心：支持幂等转账与冲正、
并发安全的复式记账、以及时间窗口对账与差异分类。不依赖网络、真实凭据或任何外部服务。

- Go 版本：见 `go.mod`（Go 1.25+，本地以 Go 1.26 验证）
- 第三方依赖：无
- 金额单位：**分（int64）**，全程整数运算，杜绝浮点误差

## 目录结构

```
internal/domain/model.go        账户、凭证、分录、幂等记录、对账差异等领域类型
internal/ledger/ledger.go       复式记账核心：幂等转账/冲正/入金、并发控制、余额与流水查询
internal/ledger/ledger_test.go  并发重复提交、幂等冲突、余额不足、冻结、冲正追溯等测试
internal/reconcile/reconcile.go 时间窗口对账：守恒校验、缺账/多账/重复/金额不符/余额不符分类
internal/reconcile/reconcile_test.go  对账差异分类与窗口口径测试
cmd/demo/main.go                本地演示：串联幂等、并发、冲正、对账五个场景
```

## 一、账务模型

### 账户与记账方向

- 所有账户均为资产类账户：**借方（Debit）表示资产增加，贷方（Credit）表示资产减少**。
- 账户余额 = 该账户全部已过账分录的带符号净额之和（借为正、贷为负）。
- 账户有状态：`正常(Active)` 允许入账；`冻结(Frozen)` 拒绝一切入账（转账与冲正均受约束）。

### 凭证（Voucher）与分录（Entry）

每次账务动作产生一张不可变凭证，凭证由两条金额相等、方向相反的分录组成：

| 凭证类型 | 借方 | 贷方 | 说明 |
|---|---|---|---|
| 转账 `VoucherTransfer` | 收款方 | 付款方 | 借收款方（资产+），贷付款方（资产−） |
| 冲正 `VoucherReversal` | 原付款方 | 原收款方 | 与原转账方向相反；`ReverseOf` 指向原凭证 ID |
| 入金 `VoucherOpening` | 入账账户 | 内置账户 `__OPENING_EQUITY__`（期初权益） | 用于期初注资，保证全系统借贷守恒 |

- **复式守恒**：每张凭证借方合计恒等于贷方合计；全系统所有分录净额之和恒为 0。
  测试中通过 `TotalDebitCredit` 和全系统净额断言这一不变量。
- 凭证 ID 有类型前缀（`TV-` 转账、`RV-` 冲正、`OP-` 入金），单调递增、可排序。
- 冲正凭证通过 `ReverseOf` 字段与原始转账凭证建立**可追溯关联**，
  账本同时维护“原始凭证 → 冲正凭证”的反向索引（`ReverseVoucherOf`）。

### 并发安全

`Ledger` 内部使用单一互斥锁，**所有写操作都在同一把锁内完成“全部校验 + 整体过账”**：

- 校验阶段不产生任何分录；只有全部前置条件通过才落库，因此
  **余额不足、账户冻结、账户不存在等失败路径绝不产生部分入账**。
- 余额检查与扣减在锁内原子完成，并发争抢余额时不会超扣，也不会丢失更新。
- 已通过 `go test -race -count=3` 反复验证无数据竞争。

## 二、幂等与冲正规则

### 幂等标识与内容指纹

- 每个请求必须携带业务幂等标识 `RequestID`（空标识直接拒绝：`ErrEmptyRequestID`）。
- 账本为每个已**成功受理**的请求记录内容指纹：
  - 转账：`transfer|<付款方>|<收款方>|<金额>`
  - 冲正：`reversal|<原始凭证ID>`
  - 入金：`opening|<账户>|<金额>`
- 处理顺序：**先查幂等记录，再做业务校验**，保证重复请求无论何时到达结论都一致。

判定结论（三种，严格区分）：

1. **首次请求**：校验通过后过账，记录 `RequestID → 指纹 + 凭证ID`。
2. **完全相同的重复请求**（同 `RequestID` 同指纹）：直接返回**首次创建的同一张凭证**，
   绝不重复记账，余额与分录数不变。
3. **内容冲突的重复请求**（同 `RequestID` 但指纹不同，如金额或收付款方被篡改）：
   返回可 `errors.Is(..., ledger.ErrIdempotencyConflict)` 解包的错误，拒绝过账。
   错误信息同时包含请求标识、已存指纹与本次指纹，作为可解释的判定依据。

> 注意：被业务规则拒绝的请求（如余额不足）**不占用**幂等键；条件满足后用同一
> `RequestID` 重试可以成功。这避免了一次临时性失败把业务标识永久“毒死”。

### 转账失败原因（均可通过 `errors.Is` 区分）

| 错误 | 含义 |
|---|---|
| `ErrEmptyRequestID` | 请求标识为空 |
| `ErrInvalidAmount` | 金额 ≤ 0 |
| `ErrSameAccount` | 付款方与收款方相同 |
| `ErrAccountNotFound` | 账户不存在 |
| `ErrAccountFrozen` | 付款方或收款方账户冻结 |
| `ErrInsufficientFunds` | 付款方余额不足（先校验付款方再收款方，无部分入账） |
| `ErrIdempotencyConflict` | 同标识重复请求内容不一致 |

所有错误都包装为 `*RequestError`，其 `Error()` 输出
`[操作] 请求标识=... 失败原因=...；判定依据: ...`，并支持 `Unwrap` 解包到底层原因。

### 冲正规则

- 只能冲正**转账凭证**（冲正入金凭证报 `ErrOriginalNotTransfer`），原始凭证不存在报
  `ErrOriginalNotFound`。
- 一张原始转账凭证**只允许冲正一次**，再次冲正报 `ErrAlreadyReversed`。
- 冲正金额与收付方**从原始凭证解析**，调用方无法篡改冲正内容。
- 冲正同样校验双方账户状态；且原收款方当前余额必须足以退回（防止余额变负），
  不足时报 `ErrInsufficientFunds`，不过账。
- 冲正请求自身也有独立 `RequestID`，遵守与转账相同的幂等规则。
- 冲正过账后，双方余额还原为转账前状态；冲正凭证与原始凭证双向可查。

## 三、对账口径

对账入口：`reconcile.Reconcile(reconcile.Input{...})`，输出
`*domain.ReconcileReport`。**对账只读不改：只报告差异，绝不静默忽略，也绝不自动修复。**

时间窗口为 **左闭右开 `[WindowStart, WindowEnd)`**：
凭证按 `PostedAt`、外部流水按 `OccurredAt` 过滤；恰好等于左边界包含、恰好等于右边界排除。

对账分三层：

1. **凭证守恒校验**：窗口内每张凭证借方合计必须等于贷方合计，否则报
   `凭证借贷不守恒`，并给出借/贷金额。
2. **业务配对**（按业务幂等标识 `RequestID` 一一配对；入金属系统内部账务，不参与配对）：

   | 差异类型 | 判定条件 |
   |---|---|
   | `缺账` | 外部渠道有该 `RequestID` 流水，窗口内账本无凭证 |
   | `多账` | 账本有该 `RequestID` 凭证，外部渠道无流水 |
   | `重复` | 同一 `RequestID` 的外部流水出现多条（给出重复渠道流水号） |
   | `金额不符` | 双方都有，但金额不一致；或金额一致但收付方不一致 |

   - 冲正凭证的外部流水按**原始转账业务的收付方方向**描述；若原始凭证也在窗口内，
     则连收付方一起核对；若原始凭证跨窗口，则只核对金额。
3. **余额核对**：对 `EndingBalances` 中给出的每个账户，重放窗口内全部凭证求净额，校验

   ```
   期初余额(StartingBalances) + 窗口内凭证净额 == 期末余额(EndingBalances)
   ```

   不一致报 `余额不符`，并给出双方数值与差额。典型成因是并发丢失更新或余额/流水被篡改。

每条 `Issue` 都携带差异类型、请求标识（或账户号）、凭证号与中文判定依据；
`Report.Balanced()` 返回是否完全无差异。

## 四、本地验证方法

所有命令均可离线执行，无需任何配置、凭据或外部服务。

```bash
# 1. 一键运行全部单元测试（含并发重复提交、余额不足、对账差异等场景）
go test ./...

# 2. 带竞态检测并反复多轮（验证并发安全）
go test -race -count=3 ./...

# 3. 静态检查
go vet ./...

# 4. 运行端到端演示（幂等/并发/冻结/冲正/对账五个场景）
go run ./cmd/demo
```

### 测试覆盖要点

- `TestConcurrentDuplicateSubmissions`：50 笔业务 × 20 次并发重复提交，
  断言凭证数恰好 50、每笔业务的全部重复返回同一凭证 ID、分录数精确、余额守恒。
- `TestConcurrentBalanceContention`：30 笔转账争抢仅够 10 笔的余额，
  断言恰好 10 成功 / 20 余额不足，无超扣、无丢失更新。
- `TestIdempotentDuplicateTransfer` / `TestIdempotencyConflict`：
  重复提交返回同一凭证且不重复记账；内容冲突被拒绝且错误可解包、信息含标识与指纹。
- `TestInsufficientFunds` / `TestFrozenAccountRejected`：失败路径无任何部分入账，
  失败信息含请求标识与判定依据；失败不占用幂等键。
- `TestReversalTraceAndEffect` / `TestReversalGuards`：冲正余额还原、借贷守恒、
  与原凭证双向可追溯、重复冲正幂等、二次冲正/冲正入金/余额不足均被拒绝。
- `reconcile` 包：干净数据相符；缺账、多账、重复、金额不符、收付方不符、
  凭证不守恒、1 分余额篡改、左闭右开窗口过滤均被正确分类。

## 五、设计边界（刻意保持的简化）

- 账本为**进程内内存实现**，不落盘、不跨进程；持久化与崩溃恢复不在本范围内，
  但领域模型（凭证不可变、幂等记录、冲正关联）可直接平移到事务型存储。
- 单一互斥锁优先保证正确性与可解释性；高吞吐分片锁等优化不属于本次目标。
- 冲正采用“再做一笔反向凭证”的红字冲正思路，原凭证保留不删，审计链完整。
